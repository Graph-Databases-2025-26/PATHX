## Project Overview and Objectives
This project investigates the integration of Large Language Models (LLMs) into database query execution pipelines, following and extending the design principles introduced by the GALOIS framework.
The primary focus is on understanding how LLM-driven operators can be systematically embedded into relational query processing, and how different optimization strategies impact result quality, execution cost, and scalability.
The project provides an end-to-end experimental reproduction of the GALOIS framework, including multiple baselines and optimized variants, evaluated across heterogeneous datasets and query workloads.

### Objectives
- Hybrid Query Processing Analysis
Study how LLM-assisted execution plans interact with classical database operators, and evaluate the effectiveness of hybrid execution strategies compared to traditional SQL and Natural Language (NL) baselines.
- Quality Evaluation of LLM-Driven Retrieval
Quantitatively assess the accuracy and completeness of query results using the metrics defined in the GALOIS paper: Cell-level F1, Cardinality Accuracy, Tuple constraint accuracy amd Aggregated AVG-Score
- Optimization Strategy Assessment
Analyze the impact of logical and physical optimizations, including: predicate push-down straegies, table-scan vs key-scan selection, automatic plan selection (Galois A, Galois F)
- Cost–Quality Trade-off Analysis
Measure the trade-offs between result quality and execution cost by tracking total token consumption, number of execution iterations and average query execution time
- Reproducibility and Experimental Transparency
Provide a modular, fully reproducible experimental pipeline implementing NL and SQL baselines, multiple GALOIS variants and automated evaluation and reporting scripts aligned with the original paper

## Project Baselines

This project implements and evaluates multiple baseline query-answering pipelines to provide a controlled comparison against the GALOIS framework.
All baselines are designed to be provider-agnostic, reproducible, and directly comparable through a unified evaluation protocol.

The following baselines are supported:
- Natural Language (NL) Prompting
The LLM receives a natural language question together with the database schema and produces an answer directly.
- SQL Prompting
The LLM receives a SQL query with the database schema context.

### Standard Baseline Workflow

All baselines follow the same **standardized execution pipeline**, implemented using **LangChain (LCEL)** for sequential orchestration:

1. **Context Building**  
   Database schema extraction and preparation.

2. **Prompt Preparation**  
   Prompt templates rendered via **Jinja2** with injected schema and query information.

3. **LLM Invocation**  
   Provider-agnostic API call (e.g., Watsonx, Gemini) with automatic measurement of latency and token usage.

4. **Result Parsing & Validation**  
   Strict parsing into a unified **FULL JSON** format with structural validation.

This uniform workflow guarantees fair comparison across baselines, datasets, and providers.

### Baseline NL & SQL: Internal Knowledge Evaluation

Both NL and SQL baselines are designed to evaluate the LLM’s **internal knowledge and reasoning ability**:

- **Context Category**: *Internal Knowledge (IK)*  
  Only the **database schema** is provided to the LLM.  
  No factual table rows or raw tuples are exposed.

- **Objective**  
  Assess how effectively the LLM can interpret schemas, reason over SQL semantics, and generate correct answers without direct data access.

Both baselines share the same provider-agnostic execution architecture and differ only in prompt formulation.

### Input Handling

**SQL Baseline**  
Queries are loaded from **data/<dataset_name>/queries_<dataset_name>.sql**
**NL Baseline**  
Queries are loaded from **data/<dataset_name>/queries_<dataset_name>.txt**

Queries are automatically associated with the corresponding dataset schema during execution.

### Result Standardization

All baselines output results using the same **unified JSON schema**, ensuring direct comparability across NL and SQL baselines, GALOIS variants, datasets and LLM providers.

Each result includes:
- the predicted result set (columns and rows),
- execution time,
- token usage,
- evaluation metadata.

## GALOIS implementation

This module implements the GALOIS query execution engine, a database-style framework for executing SQL queries over Large Language Models (LLMs).
The implementation closely follows the design and optimization principles introduced in “Logical and Physical Optimizations for SQL Query Execution over Large Language Models” (SIGMOD 2025)

### System Architecture

The system is fully modular and separates responsibilities across query parsing, confidence estimation, execution planning, and post-processing.
In GALOIS, the LLM is treated as a logical data storage layer, while query execution, optimization, and result validation are handled by a DBMS-style middleware.
Unlike NL or SQL baselines, GALOIS decomposes SQL queries into logical and physical operators, enabling iterative, structured data extraction with explicit cost–quality trade-offs

### Query Execution Model

Given an input SQL query and a database schema, GALOIS executes queries in three stages:
1. Logical plan generation
The SQL query is parsed and decomposed into a relational algebra tree.
Selection predicates may be pushed into the scan operator or evaluated locally.
2. Physical plan selection
Each logical scan operator is mapped to a physical scan strategy:
- Table-scan
- Key-scan
- Confidence driven selection
3. Iterative LLM execution and post-processing
Scan operators interact with the LLM via structured prompts.
All other relational operators (selection, projection, join, grouping, distinct) are executed locally on retrieved tuples.

### Logical Operators
The logical plan supports a subset of relational algebra operators, aligned with the paper:

| Operator          | Description                                                         |
|-------------------|---------------------------------------------------------------------|
| `LLMScan`         | Retrieves tuples from the LLM without predicate pushdown            |
| `Filter-LLMScan`  | Retrieves tuples from the LLM subject to pushed-down predicates     |
| `Selection`       | Applies WHERE conditions locally                                    |
| `Projection`      | Selects required attributes                                         |
| `Join`            | Joins relations on join conditions                                  |
| `Distinct`        | Removes duplicate tuples                                            |
| `Grouping`        | GROUP BY and aggregation                                            |

Predicate pushdown is treated as a quality-sensitive optimization, not purely cost-driven.

### Physical Scan Operators
GALOIS implements two physical scan operators, both executed iteratively.

#### Table-Scan
Retrieves entire tuples directly from the LLM. Uses an iterative prompting strategy:
- First prompt requests structured data in JSON format.
- Subsequent prompts request additional tuples, if any.
Provides strong contextual grounding but may return incomplete results for rare values.

#### Key-Scan
First retrieves key values only (e.g., primary identifiers). Then issues independent prompts to populate remaining attributes for each key. Approximates an index scan using LLM reasoning.

### Logical Optimizations (Predicate Pushdown)
GALOIS explores multiple logical plans by varying predicate pushdown strategies:

- No pushdown
All predicates evaluated locally after retrieval.
- Push-all
All WHERE predicates included in the LLM prompt.
- Selective pushdown
Only a subset of predicates pushed down.

Unlike traditional DBMSs, predicate selectivity is estimated using the LLM itself.
The model is prompted to assess confidence for each predicate, and only predicates classified as high confidence are pushed down.

#### Physical Optimizations (AUTO Mode)
In AUTO mode, GALOIS selects between Table-Scan and Key-Scan dynamically.
For each query, the LLM estimates its confidence in retrieving key values.
The confidence score is propagated to the query level and compared against a threshold τ.
- If confidence ≥ τ → Key-Scan
- Otherwise → Table-Scan
The threshold τ is calibrated per model and dataset, following the methodology described in the paper.

#### Implemented GALOIS Variants
This project implements the following GALOIS variants:
| Variant     | Description                                                                 |
|-------------|-----------------------------------------------------------------------------|
| `GALOIS_WO` | Without optimizations; retrieves data cell-by-cell (highest cost baseline) |
| `GALOIS_A`  | Pushes all predicates; always uses Table-Scan                               |
| `GALOIS_S`  | Pushes selectively based on estimated predicate selectivity                 |
| `GALOIS_F`  | Full system with confidence-based logical and physical optimization          |

Each variant outputs results in a unified JSON format to enable direct comparison.

#### Output and Metrics

For each query execution, GALOIS records:
- Retrieved tuples (normalized and validated)
- Total token usage
- Execution time
- Iteration count
- Evaluation metadata
  
These outputs are consumed by the evaluation pipeline implementing:
- **F1-Cell**
- **Cardinality Accuracy**
- **Tuple Constraint Accuracy**
- **AVG-Score**
